feat(dashboard): E2-2 speakLine —— 「朗读状态」念的那两句（纯函数）

Phase6 E2 的 web 页面要有一句「朗读状态」：念**选中那个宿舍**的温湿度、状态、
事件。和看板自己到点念的 alertLine 不是一回事 —— 那一句是说给「没在看屏幕的
人」听的，只挑最要紧的那件事说；这一句是**有人点名要听**的时候念的，点名的人
想听的就是读数本身。

两句，不是一个长句
    dorm-b 温度 31 摄氏度，湿度 60%，偏热，已持续 20 分钟。事件处理中，之后又收到 2 条异常。
温湿度一句、事件一句，中间断开 —— 一口气念完的话，听的人抓不住哪儿是数字、
哪儿是状态。结尾照旧是句号。

为什么温湿度也要念
「偏热」是 core 那套阈值算出来的结论。只听结论的话，31℃ 和 39℃ 听起来一模一样，
而这两个数对「要不要现在回宿舍关窗」完全是两件事。这是全项目唯一一个会念出这
两个数字的出口，因为它是唯一一个问的人明确想听的出口。数字一律从快照的
`node.temperature` / `node.humidity` 原样搬，这个文件里没有一个写死的读数。

和前两个出口的关系
挑谁这一条和 focusBanner / alertLine 完全相同（被点名 > 是重点），三处只能有一
份挑法：横幅说 A、念出来的是 B 的话，站在旁边听的人看不出哪里不对 —— 所以
tests/logic.test.js 里那一组「横幅和语音说的是同一个宿舍」的检查扩成了三条出口
一起对。

两句都不是自己判的：
- 「已持续 20 分钟」直接用 core 算好的 durationText（正常节点是 null，所以那句
  「已持续」根本不会出现 —— 说成「不到 1 分钟」是在说一件没发生过的事）；
- 事件那一段读的是**事件表**（openEvent 的 state），不是节点的 status。两者可以
  不一样：处理之后连着几条正常、还没到恢复的条数时，status 已经是「正常」而案卷
  还开着，那时候念「正常」是对、念「没有未结案的事件」就错了。

E2 新加的那半句：现场快照张数
读的是 core 报的 `cameraCount`（写进事件 view() 的那个数），**不是**这边数
snapshots 数组的长度 —— 那个数组每个周期都要重发，所以 core 只报个数。缺这个
字段（旧版 core）按「这一帧没带这个数」处理，不是「一张都没拍」；一张都没拍时
干脆不提这半句，不然每次朗读都先念一句「0 张」，把它的重要性抬到和温湿度一样。

传了 nodeId 就念那一个
「查看 dorm-b」之后紧跟着一句「朗读状态」，听的人要的是 dorm-b，不是 core 排出
来的那个重点。空串 / 纯空白当没传（页面上那个值是从快照里读出来的，读到
undefined 拼出来就是空串）。点了名的宿舍如果 core 还没收到过数据，就如实说
「还没有收到数据」，**不去念别人的读数** —— 那等于把「dorm-b 现在什么情况」答成
了「dorm-a 现在什么情况」，而听的人分不出这个区别。

验证
- node tests/logic.test.js 251 -> 280 条，全绿。新增里有一组是「变异」（P 段）：
  把快照里的温湿度换掉，念出来的数字跟着变 —— 写死一份文本的话这条立刻红。
- 导出清单 18 -> 19，新增的 cameraCountOf 是一条内部件（不许导出：同一件事只留
  一份说法），也加进了那条「内部件不导出」的检查。
